# Umaru

Workspace chat/voice kiểu Discord cho **Dev & Nhóm học**, tích hợp AI. Song song VN + Quốc tế (EN mặc định, toggle VI).

> **Lộ trình & phân tích sản phẩm:** xem [ROADMAP.md](./ROADMAP.md) — các quyết định chiến lược ở §0.1 và §7.
> **Tài liệu kiến trúc:** [data-model.md](docs/data-model.md) · [gateway-protocol.md](docs/gateway-protocol.md) · [ADR](docs/adr/README.md) · DDL [db/migrations/0001_init.sql](db/migrations/0001_init.sql)

## Cấu trúc

```
umaru/
├── apps/
│   └── web/              # React + TypeScript + Vite + Tailwind (client web)
├── packages/
│   ├── protocol/         # Types + codec dùng chung: snowflake, permissions (resolve), gateway events
│   └── sdk/              # API client + Gateway WebSocket client (reconnect/resume)
├── services/
│   └── api/              # Fastify REST + gateway ws, PostgreSQL (G1)
├── docs/                 # data-model, gateway spec, ADR
├── db/migrations/        # PostgreSQL DDL (áp bằng services/api)
├── ROADMAP.md            # Phân tích chức năng Discord + lộ trình G0→G5
├── turbo.json            # Đồ thị task (build/dev/typecheck/test)
└── pnpm-workspace.yaml
```

Sau này thêm: `apps/desktop` (Tauri/Electron), `apps/mobile` (React Native), `packages/ui`.

## Chạy nhanh

```bash
pnpm install
pnpm build              # build protocol → sdk → api → web
pnpm typecheck && pnpm test
```

### Chỉ client web

```bash
pnpm dev:web            # http://127.0.0.1:5173
```

`pnpm dev` chạy **cả** web và API (API cần PostgreSQL đang chạy, xem dưới). Vite proxy `/api` (kể cả WebSocket) sang `127.0.0.1:4000` nên web gọi same-origin, không cần CORS.

### Backend G1 (REST + realtime gateway)

Cần PostgreSQL 16. Dev bằng Docker:

```bash
docker run -d --name umaru-pg-dev \
  -e POSTGRES_USER=umaru -e POSTGRES_PASSWORD=umaru -e POSTGRES_DB=umaru \
  -p 55432:5432 postgres:16-alpine

cd services/api
cp .env.example .env          # sửa JWT_SECRET khi deploy thật
pnpm dev                      # migrate + listen http://127.0.0.1:4000
```

API đã có (`/api/v1`): `auth/register|login|refresh|logout`, `users/@me`, `users/@me/avatar` (PUT/DELETE), `users/:id/avatar/:uploadId` (phục vụ ảnh đại diện), `users/@me/guilds`, `users/@me/channels` (list DM + group DM / tạo DM 1-1 / tạo **group DM**), `channels/:id/recipients` (thêm, rời/mời ra khỏi nhóm), `users/@me/read-states`, `users/@me/mentions` (mentions inbox), `guilds` (+`channels`, `roles`), `channels/:id/messages` (cursor `before`; **multipart** khi gửi kèm tệp), `attachments/:id` (tải tệp, kiểm `VIEW_CHANNEL`), `channels/:id` (PATCH tên/topic/**category**/**position**), `channels/:id/overwrites` (ghi đè quyền theo kênh), `channels/:id/read`, `messages/:id`, `channels/:id/messages/search` + `guilds/:id/messages/search` (tìm tin, `q` 2–100 ký tự), `channels/:id/pins` (tin đã ghim), `messages/:id/pin` (PUT/DELETE), `channels/:id/typing`, `channels/:id/voice` (PUT vào / DELETE rời phòng thoại), `channels/:id/voice/token` (token LiveKit), `guilds/:id/voice-state` (PATCH tự mute/deafen), invites, `auth/verify-email` (+`/resend`), `users/@me/blocks` (chặn/bỏ chặn), `users/@me/friends` (+`/:id/accept`, DELETE dùng chung cho huỷ kết bạn/từ chối/huỷ lời mời), `users/@me/settings` (quyền riêng tư DM), `users/@me/message-requests` (+`/:channelId/accept`, `/:channelId/decline`), `reports` (báo cáo vi phạm), `admin/status` + `admin/reports` (hàng đợi cho người vận hành), `push/public-key` + `push/subscriptions` (POST/DELETE) + `push/test` (thông báo đẩy), `gateway` + `gateway/ws`.

## Stack (đã chốt — ROADMAP §4)

| Lớp | Chọn |
|------|------|
| Web | React + TS + Vite, Tailwind, Zustand (state + gateway), `@umaru/sdk` |
| Chia sẻ logic | pnpm + turborepo, `@umaru/protocol`, `@umaru/sdk` |
| API + gateway | TypeScript: Fastify + `ws` ([ADR-0004](docs/adr/0004-backend-typescript-first.md)) |
| DB | PostgreSQL 16 (Neon khi deploy), snowflake `BIGINT` làm khoá |
| Mật khẩu / token | argon2id (`@node-rs/argon2`), JWT HS256 access 15 phút + refresh opaque xoay vòng |
| Thoại | **LiveKit Cloud** (region Singapore) — kết nối từ G2 |
| Ngân sách | 0đ/tháng — free tier (ROADMAP §4.4) |

## Giai đoạn hiện tại

**G1 — MVP nhắn tin (đang làm).** Đã chạy được end-to-end:

- Auth email/password (argon2id), access + refresh token xoay vòng, logout thu hồi.
- Server (guild) + role `@everyone` + kênh `#general` mặc định, invite link.
- Kênh text/voice/category, sửa/xoá kênh theo `MANAGE_CHANNELS`.
- Tin nhắn: gửi/đọc (cursor theo snowflake)/sửa/xoá, reply, typing indicator.
- **DM 1-1** (`dm` channel, `guildId = null`, 2 dòng `channel_members`): mở lại cuộc cũ thay vì tạo trùng (advisory lock theo cặp user), tin nhắn chạy đúng cùng đường `messages` + fan-out như kênh thường; `DM_CHANNEL_CREATE` đẩy sang người nhận khi có người mới mở DM.
- **Badge chưa đọc + badge mention** (bảng `read_states` + `message_mentions`): `POST /channels/:id/read` (ack tới một tin hoặc tin mới nhất, `GREATEST` nên không lùi mốc), `GET /users/@me/read-states`; `READY` kèm `readStates[]` (`unread` + `mentions`) nên mở app là thấy đúng số tin. Tin do chính mình gửi không tính; đang mở kênh thì tự ack. Badge **đỏ** hiện số lượt bị `@`mention (tách khỏi badge xanh tin thường), parse `@username` khi gửi/sửa tin. Đọc trên một thiết bị thì thiết bị khác tắt badge ngay qua event **`READ_STATE_UPDATE`** (state đọc lại từ DB sau `GREATEST`, nên không phụ thuộc tab nào ack trước). **Mentions inbox**: `GET /users/@me/mentions` (cursor `before`, `limit`) trả tin có `@mình` mới nhất trước kèm kênh + tên server + người gửi (DM kèm người nhận); lọc `VIEW_CHANNEL` **trong SQL** trước `LIMIT` nên mất quyền là dòng biến mất, không lộ id kênh ẩn.
- **Xác thực email**: đăng ký xong là gửi mail kèm link `/?verifyToken=...` (token 32 byte base64url, DB chỉ lưu `sha256`; dùng một lần, hạn 24h). `POST /auth/verify-email` (công khai) và `POST /auth/verify-email/resend` (cooldown 60s → 429; đã xác thực → 409; gửi lại thì token cũ bị vô hiệu). Chưa có `SMTP_URL` thì mail ghi ra log server để dev tự bấm link; bật `SMTP_URL` là gửi thật. Response đăng ký kèm `devVerificationToken` **chỉ khi** `EMAIL_VERIFICATION_ECHO` bật (mặc định bật ở dev/test, tắt ở production). Chưa xác thực **không bị khoá đăng nhập** — app hiện thanh nhắc + nút gửi lại; token được xoá khỏi thanh địa chỉ ngay khi dùng.
- **Chặn & báo cáo**: `PUT/DELETE /users/@me/blocks/:userId` + `GET /users/@me/blocks`. Chặn **một chiều trong DB** (bảng `relationships` sẵn có, `type='blocked'`) nhưng **hiệu lực hai chiều**: không tạo được DM, không gửi được tin trong DM cũ, lịch sử DM không đọc được, DM biến khỏi danh sách của cả hai, và tin của người đã chặn nhau không còn trong mentions/search. Chặn cũng cắt quan hệ bạn bè/lời mời đang có. Tin trong **kênh server vẫn hiện** (block là chuyện giữa hai người, ẩn nội dung cộng đồng là việc của moderation). `POST /reports` (báo cáo tin hoặc người, 8 lý do, tối đa 20 báo cáo/giờ) **sao lưu nội dung tin vào báo cáo** để xoá/sửa tin sau đó không mất bằng chứng; báo cáo tin trong kênh không xem được → 404 (không dò được id tin riêng tư). UI: 🚩 báo cáo + 🚫 chặn khi hover tin của người khác, hộp thoại chọn lý do, panel 🛡 **Người đã chặn** để bỏ chặn.
- **Hàng đợi báo cáo cho người vận hành**: `GET /admin/status` (client biết có hiện lối vào không), `GET /admin/reports?status=open|reviewing|closed` (mới nhất trước, cursor `before`, kèm snapshot nội dung + số đếm theo tab) và `PATCH /admin/reports/:id { status }`. Admin khai báo bằng env `ADMIN_USERNAMES` / `ADMIN_USER_IDS` — **để trống thì không ai là admin** (mặc định đóng, an toàn khi quên cấu hình). Thiếu quyền → 403, chưa đăng nhập → 401. Không trả email của ai. UI: trang riêng `/admin/reports` (tab theo trạng thái, nút Đang xem xét / Đóng / Mở lại), lối vào ⚑ ở chân sidebar chỉ hiện khi tài khoản là admin.
- **Terms/Privacy EN/VI**: nội dung duy nhất ở `apps/web/src/lib/legal.ts` (phiên bản ở `LEGAL_VERSION` trong protocol), mở được khi chưa đăng nhập tại `/terms` và `/privacy` (`?lang=en|vi`). Đăng ký **bắt buộc tick đồng ý** — server kiểm `acceptedTerms === true` và ghi `users.terms_accepted_at` + `terms_version`. Trạng thái bản nháp và các việc còn phải làm trước public: [docs/legal/README.md](docs/legal/README.md).
- **Tìm kiếm tin nhắn**: nút 🔍 trong khung chat → `GET /channels/:id/messages/search` hoặc `GET /guilds/:id/messages/search` (`q` 2–100 ký tự, `before` + `limit` 1–50, mới nhất trước). Tìm toàn server chỉ trả kênh đang xem được (`VIEW_CHANNEL` lọc **trong SQL** trước `LIMIT`); `%`/`_`/`\` trong từ khoá được escape nên không thành wildcard. Kết quả tô sáng từ khoá, bấm vào là mở đúng kênh, lật thêm trang nếu tin cũ hơn trang đang giữ rồi cuộn tới và tô sáng tin đó. Migration `0003_message_search.sql` thêm `pg_trgm` + GIN trigram (best-effort: thiếu quyền thì vẫn chạy, chỉ chậm hơn).
- **Gateway thật**: HELLO → IDENTIFY → READY (kèm guild + kênh + **`roles`** + thành viên có **`roleIds`** + `dms` + `readStates` + **`channelPermissions`**: quyền hiệu dụng của chính user đó tại từng kênh, server tính sẵn nên client không phải chép lại thuật toán), heartbeat/ack, fan-out `MESSAGE_CREATE/UPDATE/DELETE`, `CHANNEL_*`, `GUILD_MEMBER_ADD`, **`GUILD_MEMBER_UPDATE`** (role của thành viên vừa gán/thu — cả server đổi chip ngay), `DM_CHANNEL_CREATE`, `TYPING_START`, `PRESENCE_UPDATE`, **`PERMISSIONS_UPDATE`** (quyền của chính user vừa đổi — kênh mới, được gán/thu role, vào server — nên nút sửa/xoá bật/tắt ngay, không cần reconnect), và **resume** phát lại tin nhắn bị lỡ sau khi mất mạng.
- Quyền: `resolvePermissions` trong `@umaru/protocol` dùng chung cho REST + gateway; mất `VIEW_CHANNEL` → 404 ở API và `CHANNEL_DELETE` qua gateway.
- **Quản lý role qua API**: `GET/POST /guilds/:id/roles`, `PATCH/DELETE /guilds/:id/roles/:roleId`, `PUT/DELETE /guilds/:id/members/:userId/roles/:roleId` — phân cấp theo `position` (không đụng role cao hơn cấp mình, owner/ADMIN bỏ qua) + mask quyền (**không tạo/sửa/giao role ngoài tập quyền mình có** — chặt hơn Discord nên mod không tự phong ADMIN được), `@everyone` không xoá/gán được; đổi quyền → `PERMISSIONS_UPDATE` đẩy lại cho session đang mở, tạo/sửa/xoá role phát `ROLE_CREATE/UPDATE/DELETE` cho cả server, gán/thu role phát `GUILD_MEMBER_UPDATE`.
- **Permission overwrite theo kênh**: `GET/PUT/DELETE /channels/:id/overwrites[/:targetType/:targetId]` cho cả role và thành viên; `allow`/`deny` không được chồng bit (400), `allow` phải nằm trong quyền actor đang có (**mask** — mod không tự mở `MANAGE_MESSAGES`), target không cao hơn cấp actor (owner/ADMIN bỏ qua), `@everyone` được phép. `allow = deny = 0` = xoá override. Overwrite của **category được kế thừa** xuống kênh con (category áp trước, kênh cùng target đè sau) — `resolvePermissions` nhận `inheritedOverwrites`, backend nạp `parent_id` ở REST lẫn READY; `PATCH /channels/:id { parentId }` di chuyển kênh giữa category (`null` = ra gốc) và tính lại quyền. Mỗi thay đổi → `refreshGuildVisibility`: người mất quyền xem nhận `CHANNEL_DELETE`, người vừa được cấp nhận **`CHANNEL_CREATE`** + `PERMISSIONS_UPDATE` (trước đây chỉ có chiều mất quyền).
- **UI chat thật** ([apps/web](apps/web)): đăng ký/đăng nhập, rail server (chấm xanh khi server có tin chưa đọc), nút **Home** với danh sách DM (`@tên`) + **badge số tin chưa đọc** và **badge đỏ số lượt bị nhắc** (DM có tin mới/mention nổi lên đầu, tự xoá khi mở), modal chọn người để mở DM, danh sách kênh, **tab Mentions** (nút 🔔 trên rail kèm badge đỏ tổng lượt nhắc, danh sách tin `@mình` 50 dòng/trang có tên người gửi/kênh/server/thời gian, nút **Xem thêm** nạp trang cũ hơn qua cursor `before`, bấm một dòng là nhảy đúng kênh và ack), gửi tin hiện ngay qua WebSocket, typing indicator, **sửa/xoá tin ngay trong khung chat** (nút hiện khi hover: ✎ mở ô soạn tại chỗ, Enter lưu — Esc huỷ; 🗑 hỏi xác nhận rồi xoá; nút có ở tin của mình, và ở tin của người khác khi mình có `MANAGE_MESSAGES` ở kênh đó — lấy từ `channelPermissions` của READY; nhãn `(đã sửa)` hiện sau khi lưu; tin bị xoá biến mất khỏi cả khung chat lẫn tab Mentions), đăng xuất; **panel Server Settings → Roles** (nút ⚙ cạnh tên server, chỉ hiện khi là owner hoặc có `MANAGE_ROLES`: danh sách role xếp theo cấp, tạo role mới, sửa tên/màu 10 quyền/xoá role có xác nhận, `@everyone` không xoá được; bảng **thành viên** bấm chip để gán/thu role — mọi client khác trong server thấy đổi ngay qua `GUILD_MEMBER_UPDATE`; lỗi 403/400 của server hiện ngay trong panel), **panel Channel Settings → ghi đè quyền** (nút ⚙ trên header khi xem kênh text và có `MANAGE_CHANNELS`/`MANAGE_ROLES`: danh sách override hiện có kèm số bit cho/ từ chối, chọn target trong dropdown (`@everyone`, role, thành viên), bấm từng quyền để xoay vòng **theo role → cho phép → từ chối** và lưu ngay, nút đặt lại; kênh nằm trong category hiện **phần kế thừa (chỉ đọc)** + nút sửa category, và đổi được category chứa kênh bằng dropdown; nút ➕ tạo kênh có chọn **text channel / category**, category có ⚙ riêng trên sidebar); token tự refresh khi 401; **Gợi ý `@mention`** khi gõ `@` trong ô soạn (lọc theo username rồi displayName, `↑/↓` chọn, `Enter`/`Tab` chèn `@username `, `Esc` đóng — chỉ bật khi `@` đứng đầu chuỗi hoặc sau khoảng trắng, nên gõ email không bị nhảy popup; không tự gợi ý chính mình), **bảng emoji** (nhóm cảm xúc/mặt/biểu tượng/công việc, chèn tại con trỏ) — cả hai chèn xong **trả con trỏ về đúng chỗ** và `@username` hiện thành chip xanh khi gửi; i18n EN/VI (lưu lựa chọn).

- **Mail báo cáo vi phạm cho admin** (`services/api/src/admin/notify.ts`): có báo cáo mới → gửi mail cho **đúng những admin** khai báo ở `ADMIN_USER_IDS` / `ADMIN_USERNAMES` (không cấu hình admin = không ai nhận, fail-closed). Mail chứa lý do, tên hiển thị người bị báo cáo, vị trí (server / tin nhắn riêng), mô tả của người báo cáo và link `/admin/reports`; **không** chứa email người dùng hay toàn bộ nội dung tin (bản đầy đủ nằm sau đăng nhập admin). Ba tính chất quan trọng: (1) **fire-and-forget** — SMTP chậm/hỏng không bao giờ làm `POST /reports` treo hay trả lỗi; (2) **gộp + giãn cách** `REPORT_NOTIFY_COOLDOWN_SEC` (mặc định 300s) để 20 báo cáo dồn lại thành một mail có ghi "N báo cáo mới kể từ mail trước"; (3) tắt được bằng `REPORT_NOTIFY_EMAIL=off`, và không có SMTP thì mail ghi ra log như mail xác thực email.

- **Kéo-thả đổi cấp role** (`PATCH /guilds/:id/roles/:roleId { position }`): `position` ở đây là **thứ hạng trên xuống** (0 = trên cùng, không tính `@everyone`) — ngược chiều với `Role.position` trả về (cao = mạnh hơn), nên đừng nhầm. Server renumber lại toàn dãy `position` (M..1) và chỉ phát `ROLE_UPDATE` cho **những role thật sự đổi chỗ**, theo thứ tự mới; `@everyone` luôn `position = 0` và **không kéo được** (400). Người có `MANAGE_ROLES` nhưng không phải owner/ADMIN **không đẩy được role lên trên cấp cao nhất của mình** (403, cả transaction rollback — không để position nửa vời); kéo ngang cấp mình thì được. Khoá `pg_advisory_xact_lock` theo guild để hai người kéo cùng lúc không renumber chồng nhau. Đổi tên/quyền cùng lúc với kéo vẫn đúng và **không bao giờ phát `ROLE_UPDATE` hai lần** cho cùng một role. UI: kéo hàng role trong Server Settings → Roles (vạch xanh chỉ vị trí thả, `@everyone` không kéo được, thả đúng chỗ cũ thì không gọi API), i18n VI/EN.

Chỉ nhận video có `source === "screen_share"`, nên một client tự viết không chen được camera vào khung của người khác. Khung xem nổi ở góc dưới phải (không đẩy khung chat), mỗi người một tile kèm tên; dừng bằng nút của app **hoặc** thanh nổi của trình duyệt đều đồng bộ lại trạng thái nút. **Đèn đang nói** lấy từ `ActiveSpeakersChanged` của SFU và **không đi qua gateway**: nó đổi vài lần mỗi giây, đẩy lên server chỉ tốn băng thông và làm đèn người khác nhấp nháy theo độ trễ mạng. Danh sách được chuẩn hoá (bỏ phần tử lạ, bỏ trùng, **sắp xếp** để đổi thứ tự âm lượng không gây re-render, trần 32 người) và chỉ `set` khi tập người nói **thực sự** đổi; một người rời phòng thì chỉ người đó tắt đèn (sự kiện chỉ mang một người — gán thẳng vào danh sách là cả phòng tắt). Vòng xanh hiện trên avatar trong danh sách phòng và trên nút mic của mình; người đang `deafen` vẫn thấy đèn (không nghe được nhưng vẫn cần biết ai nói). Lỗi được phân loại thành khoá i18n (`voiceErrorNotConfigured`/`NotInChannel`/`MicDenied`/`Connect`/`Unknown`) và chỉ lỗi mạng/mic mới hiện nút **Thử lại**. **Mất mạng giữa cuộc**: LiveKit tự nối lại vài lần (UI ghi "Đang nối lại âm thanh…"); nếu nó bỏ cuộc thì `decideVoiceDrop` quyết định — không còn trong phòng → dọn im lặng, còn lượt → tự nối lại kèm backoff 1s→15s (tối đa 5 lần, jitter để cả phòng rớt Wi-Fi cùng lúc không dồn lên SFU), hết lượt → lỗi + nút **Thử lại** thay vì mãi ghi "Đang thông". **Đăng xuất cũng tắt mic**: kết nối SFU là kết nối riêng, `gateway.close()` không đóng nó. Rời phòng, **bị đưa ra khỏi phòng** (mất `VIEW_CHANNEL` → `VOICE_STATE_UPDATE` với `channelId: null`) hoặc **đổi phòng ở tab khác** đều được xử lý: tab này ngắt mic ngay, hoặc đi theo sang phòng mới — không giữ kết nối tới phòng mình không còn quyền ở.

**Thông báo đẩy khi đã đóng tab** (`services/api/src/push/` + `apps/web/src/lib/push.ts` + `apps/web/public/sw.js`, migration `0013`): khi tab đóng thì **không còn JavaScript nào của app chạy**, nên chỉ service worker mới hiện được thông báo — đây là mảnh cuối của hệ thông báo. VAPID: server **tự sinh request** qua `web-push` (không phải tự viết mã hoá `aes128gcm`), khoá công khai phục vụ ở `GET /push/public-key`, subscription lưu ở bảng `push_subscriptions` với `endpoint` làm **khoá chính** (endpoint là duy nhất toàn cầu: đổi tài khoản trên cùng trình duyệt thì `user_id` bị ghi đè, nếu không người trước vẫn nhận thông báo của kênh riêng tư). Ba quyết định quan trọng: (1) **chỉ đẩy cho người không có socket gateway đang mở** — người đang mở app đã nhận tin qua WebSocket, và push qua Google/Mozilla thường đến trễ thành thông báo "tin cũ"; kiểm `socket !== null` chứ không chỉ "có trong `sessions`", vì session còn được giữ để RESUME và người vừa đóng tab sẽ mất đúng tin đầu tiên; (2) kênh server **chỉ đẩy khi được @mention** — đẩy cho cả server 500 người vì một câu "ok" là cách nhanh nhất để người ta tắt thông báo; (3) cooldown 10 giây/người (`PUSH_COOLDOWN_SEC`) để khay thông báo không bị dội. Dọn dẹp: endpoint trả 404/410 (gỡ app, xoá dữ liệu trình duyệt) bị xoá **ngay**; lỗi 5xx thì đếm và bỏ sau 5 lần. Kiểm tra dữ liệu vào là hàm thuần: `endpoint` phải **https** (nhận `http://169.254.169.254/…` là biến server thành proxy SSRF), `p256dh` đúng 65 byte bắt đầu bằng `0x04`, `auth` đúng 16 byte — khoá sai kích thước vẫn là base64 hợp lệ nhưng chỉ nổ **lúc gửi tin**, tức là ở chỗ không ai ngờ. Client: bật bằng checkbox trong hồ sơ (xin quyền ngay trong thao tác người dùng), có nút **Gửi thử** vì "đã đăng ký" không có nghĩa là "sẽ nhận được", và trạng thái phân biệt rõ `blocked` (trình duyệt chặn) / `unavailable` (server chưa cấu hình VAPID) / `unsupported`. Bấm thông báo → mở `/?channel=<id>`; app đọc **một lần** rồi xoá tham số khỏi URL (để nguyên thì F5 lại nhảy về kênh cũ và link chia sẻ bị dính). Chưa cấu hình `VAPID_*` thì mọi route push trả **503** và không có push nào được gửi — không có trạng thái "nửa bật".

**Chạy thật (Docker)** — `Dockerfile` (hai target: `api`, `web`), `docker-compose.yml` (db + migrate + api + web), `deploy/nginx.conf`, `.env.example` ở gốc, hướng dẫn trong [DEPLOY.md](DEPLOY.md). Chỉ `web` mở cổng ra ngoài; API nằm trong network nội bộ vì nó tin `X-Forwarded-For` khi `TRUST_PROXY=1` — phơi ra là client tự khai IP. Ba chỗ đã kiểm bằng cách chạy thật chứ không chỉ đọc cấu hình: **WebSocket upgrade** qua proxy (HELLO + READY đi qua được), **SPA fallback** (`/terms` khi F5 trả `index.html`, `sw.js` và `index.html` không cache, `/assets/*` cache vĩnh viễn), và **`TRUST_PROXY`** (bật: IP A bị 429 sau 3 lần sai còn IP B vẫn vào được; tắt: IP B **cũng** bị 429 vì dùng chung IP proxy).

**Chống dò mật khẩu** (`services/api/src/auth/routes.ts`): `/auth/login` trước đây **không có giới hạn nào** — vừa là lỗ hổng dò mật khẩu vừa là DoS CPU, vì mỗi lần thử đều chạy argon2id. Nay đếm **hai khoá độc lập**: theo IP (một IP dò nhiều email) và theo email (nhiều IP dò một email), cửa sổ 15 phút, `RATE_LIMIT_AUTH_PER_IP`/`_PER_EMAIL`. Chỉ đếm lần **sai**; đăng nhập đúng thì xoá bộ đếm theo email. Kiểm **trước** khi băm. Trả đúng body `RATE_LIMITED` + `retry_after` như mọi rate limit khác (không phải `TOO_MANY_REQUESTS` trần, để client không cần nhánh riêng).

**Quyền trong UI** — panel Channel Settings và Role Settings dùng chung `apps/web/src/lib/roleUi.ts`; nay có cả **`CONNECT` (vào kênh thoại)** và **`SPEAK` (nói trong kênh thoại)**, nên chỉnh được ai vào/nói được ở từng kênh thoại ngay trong web (trước đây phải gọi API tay). Kéo-thả kênh trong sidebar (đổi thứ tự, kéo vào/ra danh mục, thả vào danh mục rỗng) đã tách logic tính đích thả sang `apps/web/src/lib/channelDrop.ts` và có 10 test — đây là chỗ dễ sai một đơn vị `position` và làm lệch cả dãy kênh.

**Rate limit (spec §7)** — [docs/gateway-protocol.md](docs/gateway-protocol.md) §7 có bảng đầy đủ; tóm tắt: `IDENTIFY`/`RESUME` 1 lần/5s/socket (đếm riêng hai loại để không đóng `4004` oan cho luồng `INVALID_SESSION` → identify lại), 120 frame/phút/socket **tính cả frame rác**, `HEARTBEAT` dư 2 frame thì bỏ qua + log chứ không đóng, 5 session/user (session **cũ nhất** bị `4003`), và `POST /channels/:id/messages` 5 tin/5s/người/kênh + 30 tin/phút/kênh — kiểm **trước** khi đọc multipart nên bị chặn là không ghi DB, không để lại tệp mồ côi, không phát `MESSAGE_CREATE`. Body `429` luôn có `retry_after` (giây). SDK đã xử lý `4003` (xoá session để IDENTIFY lại) và `4004` (chờ ≥ 5 s). Tinh chỉnh bằng `RATE_LIMIT_*`, tắt bằng `RATE_LIMITS=off` — test nghiệp vụ dùng trần rất cao để không phải chờ.

**Chạy sau proxy TLS:** `GET /gateway` trả URL `wss://` khi có `x-forwarded-proto: https` (nếu không, trang https sẽ bị chặn mixed content và gateway im lặng không kết nối). Guard xác thực đọc `Authorization: Bearer` **hoặc** `x-umaru-token` — client web gửi cả hai vì một số reverse proxy bỏ header `Authorization`; khi request tới mà không có token, server log kèm `url` + header nào có mặt để biết ngay là client quên hay proxy nuốt.

### Giới hạn đã biết của backend hiện tại

- **Đa node đã chạy được**: đặt `REDIS_URL` là sự kiện đi qua bus Redis giữa các node ([ADR-0005](docs/adr/0005-gateway-multi-node-bus.md)) **và** session + replay log nằm trong Redis ([ADR-0006](docs/adr/0006-session-replay-redis.md)) ⇒ client đổi node hay API restart vẫn `RESUME` được, không phải full resync. Giao thức với client không đổi. Không đặt `REDIS_URL` thì mọi thứ trong RAM như cũ (một node).
- Presence: nguồn sự thật vẫn là RAM của node đang giữ session; đa node thì đồng bộ qua bus (thay đổi + snapshot lúc node mới vào). Chưa đọc/ghi Redis ⇒ node chết thì người ở node đó coi như offline.
- Rate limit (spec §7) đã có cho gateway và `POST /messages` / `typing`, nhưng bộ đếm nằm **trong bộ nhớ từng process**: đa node thì giới hạn thực tế = N × cấu hình, và restart là mất trạng thái (cửa sổ ngắn nên chấp nhận được). Chuyển Redis khi lên đa node. Chưa sharding (mỗi client tự chọn node qua LB). Nén frame đã có (`permessage-deflate`).
- Tệp đính kèm + avatar lưu **đĩa cục bộ** (mặc định, đúng cho 1 node) hoặc **object storage tương thích S3/R2** khi đặt `STORAGE_DRIVER=s3` — cùng một interface `FileStore`, đổi kho không sửa route. API vẫn kiểm quyền rồi stream tệp qua chính nó, nên bucket để **private** được và chưa cần CORS; chưa dùng presigned URL (băng thông tệp đi qua API). Chưa quét virus, chưa thumbnail/resize, chưa có quota theo user (mới chỉ trần 10MB/tệp và 4 tệp/tin).
- Path param dạng id được kiểm snowflake một lần ở hook `preValidation` trong [app.ts](services/api/src/app.ts) → sai định dạng là **400 `BAD_REQUEST`** thay vì 500 kèm log lỗi DB (chạy trước cả guard xác thực, nên request không token + id sai nhận 400).
- Kênh thoại có **âm thanh, đèn đang nói, chia sẻ màn hình**; chưa có camera, chuyển vùng, hay hiệu ứng âm lượng theo từng người; token do server tự ký nên khi đổi key chỉ cần khởi động lại API. **Xoay `LIVEKIT_API_SECRET` trước khi lên production** (key trong phiên dev đã lộ trong ảnh chat). Zoom/bitrate/multi-region chưa có. Đổi **thứ tự** kênh và **cấp** role đều đã kéo-thả được (kênh: `CHANNEL_UPDATE` kèm `position`; role: `ROLE_UPDATE` chỉ cho role đổi chỗ).
- UI hiển thị **ảnh đại diện** ở danh sách DM, khung tin nhắn, tab Mentions/tìm kiếm, panel gán role và người đã chặn (chưa có ảnh đại diện server, banner, bio); chưa có panel liệt kê thành viên đầy đủ (role chỉ hiện trong panel Server Settings), chưa phân quyền ẩn kênh trên sidebar bằng tay (server đã lọc kênh không xem được).
- `PERMISSIONS_UPDATE` được phát từ: tạo/sửa/xoá kênh, tạo guild, nhận invite, mọi thao tác role (sửa/xoá quyền, gán/thu role) và mọi thay đổi overwrite. REST vẫn là nơi kiểm quyền thật — `channelPermissions` chỉ gợi ý ẩn/hiện UI.
- Client gateway (SDK) xử lý đủ các mã đóng của spec §2.1: `4000` refresh token rồi resume (hook `onAuthFailure`, web nối vào `refreshSession`), `4003` xoá session để identify lại, `4004` chờ ≥ 5 s. Heartbeat có jitter ở nhịp đầu và client dedupe theo `s` — resume replay chồng lấn không làm lặp tin nhắn.
- Mail thông báo báo cáo dùng **LogMailer** khi chưa có `SMTP_URL` (ghi ra log) và bộ đếm giãn cách nằm trong bộ nhớ process — đa node cần Redis để gộp chung.
- DM 1-1 và **group DM tới 10 người** đều đã có; chưa có privacy setting chặn người lạ nhắn (P1).
